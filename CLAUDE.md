# Hexbiblio — Project Context

Academic thesis-sharing platform: submission, browsing, comments/ratings, an AI research-advisor chatbot, and personal collections. React + TypeScript + Vite frontend, Supabase backend (Postgres, Auth, Storage, Edge Functions).

## Current infrastructure (as of 2026-08-02)

- **Frontend hosting**: Vercel, auto-deploys from the `main` branch on GitHub (`Hexbiblio/hexbiblio`). Custom domain live as of 2026-08-02: `https://www.hexbiblio.fr` (primary, serves Production), with `hexbiblio.fr` 308-redirecting to it and the original `hexbiblio.vercel.app` still valid. DNS is on OVHCloud — apex `A` record → `216.198.79.1`, `www` `CNAME` → the per-project target Vercel's dashboard shows under Settings → Domains (not a fixed value — re-check there if this domain is ever reconfigured). Getting there required first deleting OVHCloud's default domain redirection (its own separate "Redirection" tab, not Zone DNS — it had `hexbiblio.fr`/`www` both forwarding to an OVH parking page via `213.186.33.5`, which otherwise conflicts with pointing DNS straight at Vercel); one of the two redirection entries initially failed to delete with a generic OVH error and only succeeded after retrying via "Modifier" first, so if this ever needs redoing and delete fails, try edit-then-delete before assuming it's stuck.
- **Backend**: Supabase project ref `lstlboldqghczcomgxvv` — this is the user's own project, fully independent. **Do not confuse with `xyfsajxypbjgtceoqbkh`**, an old Lovable Cloud-managed project that is no longer used and should be treated as decommissioned.
- **AI chatbot** (`supabase/functions/thesis-chat`): calls Google's Gemini OpenAI-compatible endpoint directly (`https://generativelanguage.googleapis.com/v1beta/openai/chat/completions`) using a `GEMINI_API_KEY` secret set in Supabase. Model is `gemini-flash-latest` (auto-updating alias) — don't hardcode a dated version string here, `gemini-2.5-flash` got deprecated once already. This replaced a call to the Lovable AI Gateway (`LOVABLE_API_KEY`) that the function had used since it was first written — that secret was never set on the independent Supabase project after the Lovable Cloud migration, so **the chatbot had been silently broken in production** until this switch. **Verified working in prod as of 2026-07-30** (both `thesis-chat` and `submit-thesis`, below, share this same secret and key). Get a `GEMINI_API_KEY` from https://aistudio.google.com/apikey and set it as a Supabase Edge Function secret if it's ever missing/rotated again.
- **Quest system** (`src/components/ThesisQuests.tsx`): a 7-step roadmap (discipline → theme → question → thesis → method → sources → plan). Progress is derived server-side from `profiles` columns (`deriveCompleted()`, one column per quest via `QUEST_PROFILE_FIELD`) — **not** `localStorage`; that was true until the 2026-08-02 cross-device sync fix below removed it. `detectCompletedQuests` only ever checks the *next* open quest against the user's latest message — strictly sequential, a later-step cue can't skip ahead of an earlier open one — except the 7th step ("plan"), which has no chat cue at all and can only be completed from the profile page (see the writing-plan pilot entry below). `thesis-chat` also receives `currentQuest`/`completedQuests` in the request body and is prompted to redirect the student back to the current step if their message jumps ahead, rather than just following the tangent.
- **Chat self-introduction** (added 2026-07-31): `thesis-chat`'s system prompt now tells Gemini to open its very first reply in a conversation with a one-sentence self-introduction ("I'm Hexbiblio, your research mentor...") before greeting/asking the opening question — it infers "first reply" from there being no earlier assistant turn in the `messages` history it receives, there's no explicit flag for it. Never repeats later in the same conversation, per the same instruction.
- **Onboarding card — mandatory** (added 2026-07-31, made mandatory same day): a separate concept from the Quest system above — Quests track *thesis-topic* progress (discipline/theme/question/etc.), this is about the *student's own* profile context (academic level, field of study, personal interests) used to personalize guidance. [`OnboardingCard.tsx`](src/components/OnboardingCard.tsx) renders in [`ChatInterface.tsx`](src/components/ChatInterface.tsx)'s empty state whenever a logged-in student's `profiles.first_name`, `academic_level` or `field_of_study` is still empty. It's a hard gate, not a nudge: there's no skip, and when it's showing, nothing else in the empty state renders — no greeting, no input box, no suggested questions, no "how it works" — the student cannot chat until it's done. `first_name`, `academic_level` and `field_of_study` are the required fields (Save stays disabled until all three are set); `last_name` and `research_interests` (up to 5 tags) are genuinely optional, labeled as such, and don't gate anything. **`first_name` is collected here specifically because nothing else asked for it before the student needed it** — `handle_new_user()` only ever populates `username`, and the `set_thesis_author_name` trigger derives a thesis's public author from first+last name, so a student who finished onboarding would previously hit a wall at their first submission and get bounced to `Profile.tsx`. The last name is asked for at submission time instead, inline in [`SubmitThesis.tsx`](src/pages/SubmitThesis.tsx) (the one moment it's actually required), and persisted to the profile before the insert so the trigger can read it and so it's never asked for twice — keeping onboarding itself short while preserving full-name attribution. This re-evaluates on every visit from `profiles` server state (not a `localStorage` flag) — a student who filled it in previously via `Profile.tsx` directly won't be gated again, since the same two columns are what both surfaces read/write; conversely if those columns are ever cleared, the gate returns. `ACADEMIC_LEVELS` lives in [`fields.ts`](src/i18n/fields.ts) as a bilingual list (alongside `FIELDS`/`DEGREE_TYPES`) shared with `Profile.tsx` — previously `Profile.tsx` had its own English-only array. Visually it reuses the chat's own speech-bubble treatment (`MascotAvatar` + tailed bubble, see below) instead of a generic bordered card — the intent is "the mentor is asking you these questions," not a form, even though the fields themselves are still structured selects/tags (not free text) to keep the data clean against the same canonical lists used elsewhere (filters, thesis submission).
- **Discipline-aware methodology guidance + mock defense mode** (added 2026-08-05, from the competitive-analysis "mentor/accompagnement" differentiation work — see [[competitive-analysis-artifact]] and [[mentor-positioning-boundaries]] in project memory): two pieces, both in `thesis-chat`. First, `SYSTEM_PROMPT`'s methodology step no longer defaults to a generic qualitative/quantitative/mixed menu — it's instructed to ground the discussion in what's actually standard practice for the student's own discipline, reinforced a second time (not just in the static step description) via a targeted line appended to `questContext` specifically when `currentQuest === "method"`, referencing `profile.field_of_study` by name. Second, a distinct **mock-defense mode**: [`ChatInterface.tsx`](src/components/ChatInterface.tsx) gates a "S'entraîner à ma soutenance" CTA behind `allQuestsDone` (all `CHAT_QUEST_IDS` complete — the 6 chat-detectable steps, i.e. every roadmap step except the self-report-only "plan" — a mock jury needs a real thesis statement/methodology to interrogate) and, when started, sends `mode: "defense"` instead of the default `"mentor"`. Server-side, `isDefenseMode` swaps in a completely separate `DEFENSE_SYSTEM_PROMPT` (a rigorous jury persona, not the warm mentor voice) and skips `questContext`/`databaseContext` entirely — neither is relevant to a mock jury. Both modes now also receive a new `researchContext` block built from `profiles.research_theme`/`research_question`/`thesis_statement`/`methodology`/`research_sources` — fields the edge function's profile query never selected before, so the mentor previously had no memory of *what* a student had actually said for a completed step, only that its checkbox was ticked; this incidentally also makes the regular mentor mode more coherent across sessions, not just defense mode. Deliberately **excludes** three shapes of feature the user ruled out when narrowing this list — see [[mentor-positioning-boundaries]] for the reasoning (the mentor draws answers out of the student, never hands them over, edits their prose, or reports their progress to a third party); the defense-mode prompt explicitly tells the model to decline writing answers for the student and stay in character. Entering the mode starts a fresh sub-conversation (messages cleared, not mixed into the mentor thread) via a canned kickoff message, sidestepping a stale-closure bug where `setMode`/`setMessages` haven't committed yet when `streamChat` would otherwise read them — `streamChat` takes an explicit `modeOverride` parameter for exactly this one call site. Couldn't verify the actual mode switch live — needs a signed-in account with all 6 quests completed — but `tsc`/the 48-test suite stayed clean and the empty-state CTA was confirmed correctly hidden for a logged-out visitor, and a single spaced-out live test call against the deployed function (see `.claude/skills/thesis-chat-testing-safety/SKILL.md`) confirmed the jury persona responds correctly with no profile context.
- **Inactivity nudge** (added 2026-08-05, same differentiation work): a lightweight banner in [`ChatInterface.tsx`](src/components/ChatInterface.tsx)'s empty state — "tu en étais à « X »" — shown when the student returns after 3+ days without touching their current open quest. Deliberately **client-side only** (`localStorage`, key `hexbiblio:lastQuestActivity`), not a new `profiles` column or a scheduled push/email: this is "you last touched this quest a while ago, on this device," which doesn't need to be a durable, cross-device fact the way quest *completion* does, and ships with zero new backend surface (no `pg_cron`, which isn't set up on this project yet — see LEX-03 in the audit if that ever gets addressed and this could be revisited as a proactive notification instead). The timestamp resets on every message sent while a quest is still open, and dismissing the banner without engaging also resets it (so it can reappear after another 3 days rather than being silenced forever). Re-checked whenever `nextQuest` changes, not on every render, so completing the quest the nudge was about makes it disappear on its own. Couldn't be verified live — needs a real account with a genuinely stale quest, not reproducible by a fresh guest session — but `tsc`/tests stayed clean and the empty state was confirmed to render correctly (no crash, no nudge) for a logged-out visitor.
- **7th quest, "plan de rédaction" (writing plan) — pilot** (added 2026-08-05, differentiation piste 1, scoped down deliberately): the first step of the roadmap past "sources," but not the full write-up-the-thesis roadmap discussed in the competitive-analysis artifact — just one new quest, to validate the mechanism before committing to more. **Self-report only, not chat-detected**: [`ThesisQuests.tsx`](src/components/ThesisQuests.tsx)'s `USER_CUES` is now `Partial<Record<QuestId, RegExp>>` and has no entry for `plan` — a writing plan takes shape over days, not one message, so there's no single exchange a regex could reliably treat as "done" the way `"I argue that X"` confirms a thesis statement. `detectCompletedQuests` reads `USER_CUES[next.id]` with optional chaining for exactly this case (a missing entry means "can't be completed through chat," not a bug — covered by a new test). The only way to complete it is a new `writing_plan` textarea in [`Profile.tsx`](src/pages/Profile.tsx)'s "Votre projet de recherche" card, wired exactly like the other 5 quest fields (migration `20260805100000_add_writing_plan_field.sql`, plain nullable `TEXT`, same pattern as `research_theme` etc.). `thesis-chat` gets a new "Self-report step" rule that explicitly REPLACES "Staying in order" when this is the current step — without it, the model would keep trying to steer the conversation back to a step that chat literally cannot resolve, which would just corner the student. The rule also tells it never to draft the plan's content itself even if asked, matching [[mentor-positioning-boundaries]]; `researchContext` deliberately excludes `writing_plan`'s actual text for the same reason — the model has no legitimate reason to read or comment on it. **One real gotcha this surfaced**: adding a 7th `QuestId` broke `ChatInterface.tsx`'s `allQuestsDone` check (used to gate the mock-defense CTA), since it was computed as "no next quest at all" — with `plan` always sitting open until self-reported, defense mode would never have unlocked. Fixed with a new export, `CHAT_QUEST_IDS` (every quest with a `USER_CUES` entry), and `allQuestsDone` now checks that specific set instead of "every `QuestId`" — future self-report-only quests won't need this fixed again, they're automatically excluded. The inactivity nudge also got a quest-aware branch: for `plan` specifically it points at the profile page instead of implying "come back and chat about it," since chatting alone can't complete this one. Verified via `tsc` (clean), the test suite (49 passed, +1 new regression test for the `USER_CUES` optional-chaining fix), and a browser check confirming both `ThesisQuests.tsx` and the `/profile` redirect still work for a logged-out visitor — the actual quest flow needs a signed-in account to exercise live.
- **Chat bubble redesign** (added 2026-07-31): [ChatInterface.tsx](src/components/ChatInterface.tsx)'s message list now renders both roles as proper comic-style speech bubbles (rounded rectangle with a small diamond "tail" pointing back at the avatar it came from — a CSS trick, a 3×3 `rotate-45` square glued to the bubble's edge), replacing the old layout where only the user's message had a background and the assistant's was bare text. The user's avatar is a plain silhouette (`UserRound` from lucide). The assistant's avatar is [`MascotAvatar.tsx`](src/components/MascotAvatar.tsx) — a single-purpose wrapper around `public/mascot-book.png` (the user's own in-progress mascot artwork, cropped tight to its content via a one-off Python/Pillow script since the original export had a lot of transparent padding), used at both call sites (the message list and the loading indicator) instead of duplicating an `<img>` tag. It takes an optional `className` (defaults to `h-10 w-9`) so resizing it later is a prop change, not a hunt through the file. - **Admin role + moderation dashboard** (added 2026-07-31): `public.user_roles` (migration `20260731100000_add_admin_role_and_moderation.sql`) is a separate table, deliberately **not** a `profiles.role`/`is_admin` column — a client-writable role column governed only by RLS would be self-escalatable, the same bug class already fixed once for `theses.author_name`. It has zero INSERT/UPDATE/DELETE policy for `authenticated` — granting/revoking admin is only ever a manual SQL statement in the Supabase dashboard, never a feature the app exposes. A `SECURITY DEFINER STABLE` `is_admin(_user_id uuid)` function backs new permissive RLS policies ("Admins can update/delete any thesis", "Admins can update any profile" — additive to, not replacing, the existing owner-only ones, since Postgres ORs multiple permissive policies together) and an admin-aware rewrite of `lock_immutable_thesis_fields()` that skips the revert-to-`OLD` logic for admins, letting them edit `title`/`abstract`/`file_url` — locked for everyone else. A second migration (`20260801000000_admin_can_edit_author_name.sql`) applies the same admin bypass to `set_thesis_author_name()` — normally this trigger unconditionally re-derives `author_name` from the submitter's `profiles.first_name`+`last_name` on every insert/update (see Author lock below), but now skips that for admins so they can set it directly. Doesn't weaken the protection for anyone else: the function still checks `is_admin(auth.uid())` first, and on `submit-thesis`'s own INSERT path `auth.uid()` has no JWT context (it runs on the service-role key), so `is_admin()` is false there regardless — submission behavior is unchanged. Frontend: [`AuthContext.tsx`](src/contexts/AuthContext.tsx) exposes `isAdmin`/`isAdminLoading` (queried from `user_roles`, `as any`-cast like other tables missing from the stale generated `types.ts`); [`AdminRoute.tsx`](src/components/AdminRoute.tsx) gates `/admin` → [`AdminDashboard.tsx`](src/pages/AdminDashboard.tsx) (Mémoires/Comptes tabs, `table.tsx`-based); [`ThesisDetail.tsx`](src/pages/ThesisDetail.tsx)'s existing owner-only edit feature becomes `isOwner || isAdmin`, plus an admin-only delete button and admin-only title/author name/abstract/PDF-URL fields. Admin accounts also skip: the mandatory onboarding gate (`ChatInterface.tsx`), `thesis-chat`'s daily message cap, and `submit-thesis`'s daily cap + post-rejection lockout — all via the same `user_roles` lookup, done server-side in the edge functions so it can't be spoofed by anything the client sends. **Deliberately NOT bypassed for admin**: `thesis-chat`'s 3-second `MIN_INTERVAL_MS` spacing check (protects the shared `GEMINI_API_KEY` itself from a repeat of the 2026-07-29 ban, not just the student experience) and `submit-thesis`'s Gemini content-consistency check (a quality gate, not a rate control). Account deletion is a separate edge function, [`admin-delete-user`](supabase/functions/admin-delete-user/index.ts), since it needs the Auth Admin API (service-role-only) — it re-derives admin status server-side (never trusts a client-supplied flag) and refuses to let an admin delete their own account via that path. `profiles.user_id`/`theses.user_id` already `ON DELETE CASCADE` to `auth.users(id)`, so one Admin API call cleans up everything (theses, comments, ratings, bookmarks, sources) with no manual cleanup step. Migration and the one-time admin-grant `INSERT` were run by the user via the SQL Editor (the `CREATE POLICY` statements needed `DROP POLICY IF EXISTS` guards added after an initial paste half-applied and a re-paste hit "already exists" — same class of `db push`-vs-SQL-Editor gotcha as elsewhere in this file). **Verified working in prod as of 2026-08-01**: the user's own account confirmed as admin, "Admin" nav link appears, `/admin` loads instead of redirecting.
- **Thesis submission integrity** (added 2026-07-30, three phases):
  - *Author lock*: `theses.author_name` is no longer free text. [SubmitThesis.tsx](src/pages/SubmitThesis.tsx) pre-fills it (disabled) from the submitter's `profiles.first_name` + `last_name`, and a Postgres trigger (`set_thesis_author_name_trigger`, migration `20260730120000_lock_thesis_author_and_antispam.sql`, re-pointed at first/last name in `20260730140000_use_first_last_name_for_thesis_author.sql`) re-derives it from the profile on every insert/update regardless of caller — can't be spoofed via a direct API call either. `profiles.username` plays no role in authorship anymore — kept only for personalization (the `thesis-chat` greeting, comment author display in `CommentSection.tsx`).
  - *Basic anti-spam*: min length + non-repetitive-abstract checks client-side ([thesisValidation.ts](src/lib/thesisValidation.ts)) and via DB `CHECK` constraints + a unique index on `(lower(title), lower(author_name))`.
  - *AI content verification*: [submit-thesis](supabase/functions/submit-thesis/index.ts) downloads the uploaded PDF, extracts text from the first ~15 pages (see gotchas below — `unpdf` has no page-range option and blows the CPU budget on real multi-page PDFs otherwise), and asks Gemini whether it matches the declared title/field/abstract before inserting into `theses`. The `theses` `INSERT` RLS policy for `authenticated` clients was dropped (migration `20260730130000_lock_theses_insert_via_function.sql`) — this function (service-role key) is the **only** path that can create a thesis row. PDF upload is accordingly mandatory. On a content mismatch, the client only ever sees a generic rejection message — Gemini's specific reasoning is logged server-side only, never returned, so a would-be spammer can't use the response to probe where the checker's line is — and the account is locked out of further submissions for 1 hour. **Both the accept and reject paths verified working in prod as of 2026-07-30.**
  - *Bibliography extraction (Phase 3)*: a `sources` table holds citations extracted from each thesis's PDF, via shared logic in [`_shared/extractSources.ts`](supabase/functions/_shared/extractSources.ts) (see gotchas below for why it locates the bibliography through the table of contents rather than a fixed page window). New submissions trigger extraction in the background from `submit-thesis` via `EdgeRuntime.waitUntil()` (never blocks the response); [extract-sources](supabase/functions/extract-sources/index.ts) backfills already-submitted theses in small batches, gated on the raw `SUPABASE_SERVICE_ROLE_KEY` as bearer token (internal/maintenance endpoint, not user-facing — never invoke it with anything other than that key). Browsable at `/sources` ([Sources.tsx](src/pages/Sources.tsx), filterable by the parent thesis's field/degree) and as a compact numbered list on each thesis's own detail page.
  - *Post-submission edits*: authors can change `field`/`degree_type`/`graduation_year`/`keywords` on their own thesis from [ThesisDetail.tsx](src/pages/ThesisDetail.tsx) (pencil icon next to the badges, owner-only). `title`/`abstract`/`file_url`/`user_id` stay immutable — a trigger (`lock_immutable_thesis_fields_trigger`, migration `20260730160000_allow_thesis_metadata_edits.sql`) reverts any attempted change to those columns regardless of caller, since the existing "Users can update own theses" RLS policy was never column-restricted and would otherwise let a direct API call rewrite the AI-verified title/abstract/PDF.
- **Les incontournables d'un domaine** (added 2026-08-01): ranks the works most students cite, per field — the first feature to exploit the `sources` table as a corpus rather than as a per-thesis list. Migration `20260801120000_field_essentials.sql` adds an IMMUTABLE `normalize_citation_title()` (lowercase, accent-fold, collapse whitespace, strip edge punctuation) plus a `get_field_essentials(_field, _limit, _min_theses)` RPC. Surfaced as the **default tab** on `/sources` via [`FieldEssentials.tsx`](src/components/FieldEssentials.tsx); the existing full list moved to a second tab, and its query is now gated on that tab being active so it doesn't fire unseen. Clicking a work jumps to the full list pre-searched for its title. Design notes worth keeping: (1) **grouping is by normalized title, deliberately not by author or year** — author formatting swings between "Bourdieu, P." and "Bourdieu, Pierre" and years differ across editions, so title is the only stable identifier the AI parse produces; (2) accent folding uses `translate()` rather than `unaccent()` so the migration needs no extension and stays genuinely IMMUTABLE (could back an index later); (3) there's a **minimum title length of 8 characters** — without it, bad parses like `"p. 42"` appear in many bibliographies and rank *first*, which is exactly what happened in testing; (4) ranking counts `DISTINCT thesis_id`, not rows, so a duplicate entry within one bibliography can't inflate a work's standing; (5) display title/authors/year are picked by frequency then **longest** — on a young corpus nearly every work is cited two or three times with a different spelling each time, so ties are the norm and the longer string is the more complete attribution. The whole thing was validated before deploy against real Postgres via PGlite (WASM) with a fixture reproducing all of the above — see git history if it needs revisiting.
- **Pagination on `/database` and `/sources`** (added 2026-08-01): both pages previously ran `select("*")` with no `limit`/`range`, fetching the entire matching result set on every keystroke — harmless today, would silently degrade as either table grows. [`PageControls.tsx`](src/components/PageControls.tsx) is a shared control (windowed page numbers with ellipsis, icon-only prev/next since page numbers don't need translated labels, a "13–24 sur 87"-style range line) driving `.range()` on the query with `{ count: "exact" }` for the total. `PAGE_SIZE = 24` on both — chosen because it divides evenly by the existing `sm:grid-cols-2 lg:grid-cols-3` grid, so a full page never ends on a half-empty row. On `/sources` this only applies to the "Toutes les sources" tab (see the essentials feature above, which has its own bounded `LIMIT` and no pagination). Search/filter changes go through wrapper handlers (`handleSearch`/`handleFieldFilter`/`handleDegreeFilter`) that reset to page 1 *and* update the underlying state in one call — resetting via a separate effect would cause a wasted extra fetch (once for the filter change, once more when the reset lands). A side benefit on `/database`: the ratings/accuracy_ratings follow-up queries now only cover the current page's thesis IDs instead of every matching row.

Fixed: `lang="fr"`, a real bilingual-brand-voice description (tutoiement, matches `landing.subtitle`), `og:url`/canonical pointing at the real prod URL, and a proper `og:image`/`twitter:image`. The image itself — `public/og-image.png` (1200×630, the standard OG size) — is generated by a one-off Python/Pillow script (not checked in; the PNG is), not hand-designed: colors are pulled directly from `src/index.css`'s dark-mode HSL tokens (not eyeballed/guessed), and the two typefaces are the exact ones the app already loads (Libre Baskerville for the "Hexbiblio" wordmark, Source Sans 3 for the tagline), downloaded from the same Google Fonts URL `index.css` imports — so the share card and the live app are visually the same brand, not a separate one-off design. Uses the mascot (`public/mascot-book.png`) as the hero element. **Verified Vercel actually serves this as a real image despite `vercel.json`'s catch-all `rewrites` rule** — tested against an already-deployed static file (`hexbiblio-logo.svg` returns its real content, not `index.html`), confirming Vercel's rewrite only applies when no matching static file exists in the build output, so `/og-image.png` needs no `vercel.json` change to be served correctly.
- **Mémoires proches par sources partagées** (added 2026-08-01): the second feature built on the `sources` corpus, after "les incontournables" — for a given thesis, ranks other theses by how many normalized citation titles they share with it. Migration `20260801130000_related_theses_by_shared_sources.sql` adds `get_related_theses(_thesis_id, _limit, _min_shared)`, reusing `normalize_citation_title()` from the essentials migration (same grouping key, same reasoning). Surfaced on [`ThesisDetail.tsx`](src/pages/ThesisDetail.tsx) via [`RelatedTheses.tsx`](src/components/RelatedTheses.tsx), just above the comment section. Design notes: (1) **default minimum of 2 shared sources** — one shared reference is often just a common intro textbook, not a real sign of related work; (2) **deliberately not filtered by field** — an interdisciplinary citation overlap (e.g. a psychology thesis and a sociology thesis both citing the same foundational text) is a genuine, interesting signal, not noise to exclude; (3) the component renders nothing at all (not an empty state) when there's no overlap — on a young corpus that's the common case, and a "no related theses" message on every single detail page would be more noise than signal. Validated the same way as the essentials feature: real Postgres via PGlite, with a fixture proving the ranking order, the threshold cutoff, cross-field matches surviving, and — the one real bug the fixture caught — that two citations of the same work must actually match textually after normalization (a title missing a leading "The" does **not** merge, correctly, since that's a different string, not a formatting difference).
- **Dark mode** (added 2026-08-01): [`ThemeContext.tsx`](src/contexts/ThemeContext.tsx) defaults to the OS `prefers-color-scheme` and live-updates on system theme changes (a `matchMedia` `"change"` listener), but a manual toggle — the moon/sun button in [`Navbar.tsx`](src/components/Navbar.tsx) — overrides it: once clicked, the choice is persisted to `localStorage` and the system listener stops applying (it bails out early whenever `localStorage.getItem("theme")` is set). Tailwind's `darkMode: ["class"]` and the `.dark` CSS-variable block in `index.css` already existed for this; `ThemeContext` just drives the class. The switch fades instead of flashing, but the transition is deliberately scoped to a `.theme-switching` class `ThemeContext` adds for ~300ms around the toggle only, not left on globally — an always-on version made every hover/focus state without its own `transition-*` utility (inputs, textareas, select items) inherit the slow fade, which felt sluggish everywhere, not just on the switch. **Gotcha**: don't transition `stroke` alongside `color` — lucide icons set `stroke="currentColor"`, so while the parent's `color` is mid-transition, transitioning the icon's own `stroke` too starts a second animation chasing a target that's itself still moving, which visibly flickers/desyncs icons during the fade. ## Conventions / gotchas for future work

- **Multiple Claude Code sessions sometimes work on this repo at the same time** — noticed repeatedly (2026-08-01): files modified/created by another chat show up in `git status` mid-task (a whole batch of component/context files, `.claude/launch.json`, `tailwind.config.ts` at once was one instance; a stray `ThemeContext.tsx`/`App.tsx` change was another, earlier), the local dev server port (8080) is sometimes already held by another chat's server, and a `git push` can fast-forward past a commit neither you nor the current-session user made (e.g. `bf6be79` "Regenerate Supabase types... (DX-02)" landed between two pushes in this same conversation). None of this is corruption — treat it like any other collaborator's concurrent work: **never stage or commit files you didn't personally create/edit** (name files explicitly with `git add`, never `-A`/`.`), don't delete or "clean up" unfamiliar untracked files without asking, and if the dev server port is taken, start your own on a different port (`npm run dev -- --port <n> --strictPort`) rather than fighting over 8080.
- **Never interpolate a search term straight into a PostgREST `.or(...)` filter** — PostgREST reads the filter body as a comma-separated list of conditions, so any term containing a comma splits it into garbage. This shipped and broke author-style searches (`"Dupont, M."`) on `/database`, `/sources` and the admin dashboard — worst on `/sources`, where citations are made of commas. Use `buildIlikeOrFilter` in [`searchFilter.ts`](src/lib/searchFilter.ts), which quotes each value (and escapes `"`/`\`); it's covered by tests in `searchFilter.test.ts`.
- **`@tanstack/react-query` was removed 2026-08-01** — it came from the original `vite_react_shadcn_ts` scaffold (`App.tsx` wrapped everything in a `QueryClientProvider` from the very first commit) but no page ever actually called `useQuery`/`useMutation`; every page fetches via a raw `useEffect` + direct `supabase.from(...)` instead. Removed the provider and the dependency rather than keep unused boilerplate around — if a future feature genuinely needs its caching/refetch behavior, reinstall then rather than reintroducing a second data-fetching style speculatively now.

- Supabase's web SQL Editor does **not** support `COPY ... FROM stdin` blocks (psql-only) — any raw SQL given to the user to paste there must use plain `INSERT INTO ... VALUES (...)` statements.
- Don't manually cast JSON-shaped text (`{"key": "value"}`) to `::text[]` just because it starts with `{` — that broke `auth.users.raw_app_meta_data`/`raw_user_meta_data` (jsonb) during the migration. Let Postgres coerce plain string literals to the target column type instead.
- `storage.buckets`/`storage.objects` have a `protect_delete` trigger — direct `DELETE` on them is blocked by Supabase; use `ON CONFLICT DO NOTHING` on insert instead of delete-then-reinsert patterns.
- The user is comfortable following precise step-by-step instructions (GitHub web UI, Supabase dashboard, Google Cloud Console) but had no prior local git/terminal experience — this local clone is their first. Keep terminal commands explicit and check in after each one rather than batching many steps.
- **Supabase Storage keys must be S3-safe ASCII** — accented characters (very common in French filenames, e.g. "Mémoire.pdf") and other non-ASCII characters are rejected outright with `Invalid key`. Sanitize filenames (strip diacritics, e.g. via `.normalize("NFD")` + stripping combining marks, then swap any other unsafe character for `_`) before using them in a storage path — see `sanitizeFileName` in [SubmitThesis.tsx](src/pages/SubmitThesis.tsx).
- **A private `theses` storage bucket breaks every PDF link with a misleading error** (found and fixed 2026-08-02) — the app has always used `getPublicUrl()` for uploads and downloads, which only works when the bucket's `public` flag is `true`. It had been `false` since a migration flipped it 19 seconds after the bucket's own creation on day one, and nothing ever reverted that — Supabase's public-object route filters on `public = true` internally, so a private bucket surfaces as `{"error":"Bucket not found","code":"NoSuchBucket"}` on every download link, not a permission error, which is what made this hard to place at first (`storage.buckets`/`storage.objects` RLS both checked out fine, and the Supabase dashboard could open the same file — it uses an authenticated path, not the public route, so it never hit the same check). If PDF downloads ever break again with `NoSuchBucket` despite the bucket visibly existing, check `select public from storage.buckets where id = 'theses'` before anything else. Fixed with `UPDATE storage.buckets SET public = true WHERE id = 'theses'` — not a new exposure, since `storage.objects` already restricts write access to a user's own folder and every thesis is already readable by any authenticated user via the `theses` table's own RLS. **Superseded 2026-08-04** — see the LEGAL-04 entry above: the bucket is deliberately private again now that `ThesisDetail.tsx` downloads PDFs through the authenticated Storage API instead of `getPublicUrl()`.
- **`npx supabase db push --linked` fails** with a `permission denied to alter role` / login-role error — known unresolved CLI bug ([supabase/cli#5091](https://github.com/supabase/cli/issues/5091)). Workaround: `npx supabase db push --db-url "postgresql://postgres:PASSWORD@db.lstlboldqghczcomgxvv.supabase.co:5432/postgres"` (direct connection string from Dashboard → **Connect** button → **Direct** tab; DB password is separate from the anon/service_role keys — reset it from Project Settings → Database if never saved). This project has repeatedly hit `db push` recording a migration's version as applied (in `supabase_migrations.schema_migrations`) even though the run errored — the DDL itself had already succeeded by the time the bookkeeping insert failed (e.g. `duplicate key value violates unique constraint "schema_migrations_pkey"`). **Don't assume an errored push means the migration didn't apply** — verify the actual DB object first (e.g. `select tgname from pg_trigger where tgrelid = 'public.theses'::regclass;`), then mark it with `npx supabase migration repair --status applied <version> --db-url "..."` if it's genuinely already there, rather than troubleshooting the migration content. Same fix applies to a migration pasted directly into the SQL Editor, which the CLI never sees at all. Write new migrations with `IF EXISTS`/`IF NOT EXISTS` guards where possible to avoid needing this.
- **`unpdf`'s `extractText()` has no page-range option** — it walks every page of a PDF, which reliably exceeds a Supabase edge function's per-request CPU budget on a real 80-150 page thesis (`Error 546`, Supabase's `WORKER_LIMIT`). Extract text page-by-page instead (`pdf.getPage(n)` + `page.getTextContent()` on the `PDFDocumentProxy` from `getDocumentProxy()`), stopping at a fixed page count — see `extractLeadingText` in [submit-thesis/index.ts](supabase/functions/submit-thesis/index.ts).
- **Don't locate a section of a long PDF by guessing a fixed page window** (e.g. "the bibliography is somewhere in the last N pages") — real theses can carry huge annexes after it (one seen in this project: bibliography at page 82 of 227, followed by 140+ pages of interview transcripts), so any fixed window eventually misses it. Read the table of contents instead (always near the front, cheap and bounded) for the stated page number, validate against the actual heading nearby, and only fall back to a backward scan / blind guess if that fails — see `findBibliographySection` in [`_shared/extractSources.ts`](supabase/functions/_shared/extractSources.ts).
